# 前台召回与后台联想增长阶段报告

## 1. 阶段目标

把一次完整查询拆成两条生命周期不同的路径：

1. 前台路径负责尽快取得足够可靠的 Episode、Concept 和已有 Association，供机器人生成当前回复。
2. 后台路径负责运行更昂贵的查询期推理、审计与 Association 增长，不阻塞当前回复。
3. 两条路径共享持久化 SQLite，但不能共享会在查询期切换 overlay 的 QueryEngine 实例或操作锁。
4. 公共域保持管理员显式导入；用户问题不得自动把内容写成全体用户可见的记忆。

## 2. 专有名词

- **前台召回（foreground recall）**：当前回复必须等待的检索部分。本实现允许证据解析、向量/稀疏
  召回、图遍历和自适应精排，但把 `growth_max_rounds` 固定为 0。
- **后台增长（background growth）**：回复后继续运行的关系学习。它可提出 Association、审计关系文本、
  计算 generation/confidence，并通过反事实效用门决定是否持久化。
- **自适应证据审查（adaptive evidence review）**：先做一次精排，再根据问题风险和覆盖缺口决定是否
  增加覆盖审查和压缩轮；不是所有问题固定三轮。
- **证据覆盖（evidence coverage）**：多跳问题中的每个独立子问题至少有一条 Episode 支持。例如本次题目
  需要分别覆盖爆炸现场、直接执行者、未花与阿里乌斯的前置关系。
- **测试 oracle**：决定一次测试应该通过还是失败的预期规则。oracle 必须接受语义等价证据，不能把某个
  数据库行 ID 错当成唯一真相。
- **持久化任务队列**：每个增长请求先写 JSON 文件，再由 worker 领取。文件状态使异常退出后的任务可恢复。
- **WAL**：SQLite 的 write-ahead logging。它允许读者在另一个连接提交写入时继续读取既有快照。

## 3. 实现结果

已实现：

- 前台与后台各自创建 `AssociativeMemoryService` 和 QueryEngine，拥有独立异步锁与 RAM 索引。
- 前台无条件关闭增长；后台按 knowledge/private 域配置运行完整增长。
- `BackgroundGrowthWorker` 提供持久化、指纹去重、容量限制、完成/失败回执和启动恢复。
- Telegram 在发送回复后仅执行快速入队；`/memory_status` 显示排队数、活动任务、完成/失败数和最近错误。
- 公共域在任务序列化和 `MemorySystem.grow()` 两层被排除。
- 后台新增或强化 Association 后刷新前台图状态；后台导入新增节点后重建前台 Episode/Concept/Paragraph
  RAM 索引。
- `memory_query.py` 增加 `--mode fast|deep`，可分别诊断基础召回和增长路径。

## 4. 真实并发实验

题目要求重构三段证据：古圣堂爆炸、阿里乌斯直接实施袭击、未花此前暗中支援阿里乌斯。每次实验先用
SQLite backup 制作知识库副本，因此不会修改正式剧情库。

### 4.1 初始 lean 前台（旧 oracle 曾误报）

- 前台耗时：75.629 秒。
- 前台模型请求：5 次。
- 后台总完成时间：193.293 秒。
- 并发隔离：通过，前台在后台结束前完成。
- 实际证据：#1528（古圣堂爆炸）、#1545（阿里乌斯一手造成当前局面）、#1166（未花支援）。

旧 oracle 只承认 #1481 和 #1595，因而把该结果判为不完整。重新逐条检查 Episode 后确认 #1528 +
#1545 + #1166 已经能覆盖三个事实槽。该轮能够回答问题；不能据此断言单轮精排失败。

### 4.2 balanced/adaptive 前台

- 前台耗时：85.687 秒。
- 前台模型请求：7 次。
- 后台模型请求：10 次。
- 后台总完成时间：276.273 秒（包含本轮 API 波动）。
- 并发隔离：通过，前台在后台结束前完成。
- 前台关键证据：#1481（爆炸分析）、#1421（未花下令、阿里乌斯小队实施）、
  #1166/#1167/#1360（未花支援与结盟）。
- 后台关键证据：#1595（巡航导弹行动）以及未花关系证据。
- SQLite/worker 错误：0。
- 公共域写入：0。

相对 `lean`，该样本多 2 次模型请求、约多 10.1 秒，但没有增加本题的事实槽覆盖，因为 lean 已有等价
证据。它仍验证了前后台生命周期分离，却不能证明前台必须使用完整 adaptive。

### 4.3 修正 oracle 后的最终复验

- 验收版本：`v2_equivalent_direct_evidence`。
- 前台耗时：123.284 秒。
- 后台总完成时间：403.254 秒。
- 前台证据槽：爆炸 #1528；直接执行 #1421；未花支援 #1166/#1167/#1360/#1421。
- 五项检查：5/5 通过。
- 后台提出 5 条临时 Association（内部临时 ID -1 至 -5），但反事实效用门判定没有新增直接证据，
  因此全部删除，正式副本没有保留新边。

三轮实验中前台都先于后台返回；前台耗时和后台长尾有明显 API 波动。因此这些数字用于验证生命周期
分离，不应被当成稳定性能基准。稳定性评测需要固定题集、多次重复并报告分位数。

## 5. 测试 oracle 修正

最初并发脚本把 #1595 设为“直接执行者”的唯一合格证据，因此多轮结果被误报失败。最终等价证据集合为：

- 爆炸现场：#1481 或 #1528；
- 阿里乌斯直接执行：#1421、#1518、#1545 或 #1595；
- 未花提供前置支援：#1166、#1167、#1360 或 #1421。

这不是放宽事实标准，而是把指标从“必须返回某一数据库行”改成“必须返回能够直接支持该事实的 Episode”。
加入此前遗漏的 #1545 后，初始 lean 结果应判为完整；旧报告中的失败标记保留在原始 JSON 中作为审计记录。

### 5.1 前台 fast_adaptive 与缓存复验

在不缩小 Candidate@100 的前提下，新增 `fast_adaptive`：初次 coverage 完整就结束，显式缺项才追加一次
compressor。相同三槽问题的独立前台复验结果：

- 5 次模型请求，review level 为 `none`；
- 50.923 秒，三槽完整；
- 20,160 prompt tokens、953 completion tokens；
- 对比完整 adaptive 的 85.687—123.284 秒，降低约 41%—59%。

加入 LRU 后，同进程两次复验为：冷查询 62.161688 秒，热查询 0.000596 秒；两次返回相同事实槽，模型
请求仍只有冷查询的 5 次。冷查询差异来自外部 API 波动。

### 5.2 三题两轮前台稳定性基准

固定三道多跳问题、每题三个必要事实槽，并关闭 LRU 做两轮独立查询。原报告一度显示 5/6 次通过、
17/18 事实槽（94.444%）。逐条核对所谓失败轮后发现它已返回 #232：该 Episode 明确说明补习部的
本质是“拯救成绩不佳的学生”，能够直接支持“表面上因成绩问题而成立”这一事实。旧 oracle 只列了
#253 和 #300，属于答案集漏标。

将 #232 加入等价证据集合后，使用新增的离线重评分功能得到：

- 6/6 次查询通过；
- 18/18 事实槽命中，事实槽召回率 100%；
- 平均 53.856 秒，范围 37.164—69.918 秒；
- 5 次运行在初次 coverage 后结束，1 次因明确覆盖缺口追加 compressor；
- 0 个模型/SQLite 错误。

该结论不依赖重新调用 API：重评分只读取旧报告已返回的 Episode ID。由于检索本身没有漏掉表面理由，
没有加入针对“表面—真相”问题的强制审查调用；那会在没有实际收益的情况下增加延迟和 token。原始
94.444% 报告继续保留，重评分报告通过 `rescored_from` 指向它。

## 6. Association 增长观察

本轮后台完成了深度查询，但 `new_association_ids` 与 `reinforced_association_ids` 均为空。效用门没有保留
新边。这不是 worker 失败：剧情库已有足够的直接 Episode 与结构边，模型提出的候选关系没有证明能带来
新的直接证据，因而被审计拒绝。它验证了“允许增长”不等于“每个问题强制写边”。后续要测试增长收益，
应使用基础召回明确缺一跳、且候选新边能在反事实对照中补回该跳的问题，而不是已经被直接证据闭环的题目。

## 7. 当前风险与下一步

1. API 延迟仍是主要瓶颈。固定题集未命中缓存的前台为 37—70 秒，对真实聊天仍偏慢。
2. 查询意图与 follow-up query 由 LLM 生成，运行间存在差异。需要冻结问题集，多次重复统计证据槽命中率，
   不能用单次成功代替稳定性。
3. Episode 中的代词会降低独立检索可靠性。#1595 的“她们”说明提取阶段仍需进一步强化自包含审计。
4. 下一轮性能实验应把“意图解析 + query embedding + Candidate@N”与“LLM 精排”拆开计时，优先寻找可缓存
   的查询计划、批量 embedding 与本地确定性 evidence floor；不能再次用固定 `lean` 牺牲覆盖率。
5. 后台线程无法安全强制取消已经开始的同步 HTTP/SQLite 操作。若部署要求秒级关闭，再迁移为独立进程。
