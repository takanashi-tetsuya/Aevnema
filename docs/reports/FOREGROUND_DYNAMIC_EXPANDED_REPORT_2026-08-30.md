# 前台动态联想检索扩展实验报告

日期：2026-08-30  
实验对象：蔚蓝档案剧情公共知识库的前台问答检索链路  
当前提示词版本：`v3.38_entity_followup_and_authority_slot`

## 1. 摘要

本阶段先把动态问题集从 3 题扩展到 15 题、57 个必需事实槽，随后分别处理了评测资产错误、基础召回遗漏和追问规划的延迟问题。

最初一次完整基线为：

- 11/15 题完整通过。
- 53/57 个事实槽命中，事实槽召回率 92.98%。
- 平均耗时 62.187 秒，最大耗时 107.812 秒。

审计发现 4 个失败槽中有 2 个不是检索失败，而是评测答案集合不完整或标错。修正评测资产后，原结果离线重算为 13/15、55/57（96.49%）。剩余两个真实检索失败均已通过结构化答案槽和确定性证据保护修复，并分别在新的在线查询中通过。因此，目前有“组合后的 15/15、57/57”定向证据，但尚未进行一次全新的、同构条件下的 15 题完整重跑；这不能被写成稳定性已经证明。

追问规划实验表明：对每个问题无条件调用一次 LLM 生成后续检索词，不是可靠的成本收益选择。冻结计划的 A/B 中，删除追问没有降低候选或最终事实槽召回；但一次真实动态查询又证明，LLM 意图解析会发生波动，过于激进地跳过追问会漏掉权限类事实。因此当前采用保守的自适应策略：只有当问题包含“必须先回答前一实体才能解释后一指代”的链条，或初始意图查询数量较多（当前安全阈值为 12）时才保留追问规划，其余情况直接跳过。

最新动态验证中，`concept_bridge_04_hatred_political_chain` 在跳过追问规划后仍命中 3/3 事实槽，总耗时由此前约 68.176 秒降到 52.161 秒；追问规划仅耗时 0.000756 秒。该查询的最大瓶颈已经变为证据重排：37.716 秒，占全流程 72.31%。

## 2. 系统边界与数据模型

本报告只评估聊天机器人对公共剧情知识库的前台检索，不评估后台记忆增长的长期收益，也不把用户私有记忆与剧情知识混合。

当前记忆空间保持架构隔离：

- 公共知识：所有用户均可读取的剧情和普适信息。
- 用户私有记忆：以“平台 + 平台原生用户 ID”为稳定身份键隔离。
- 会话/运行数据：用于当前上下文、日志、任务回执和缓存，不替代长期记忆。

核心语义对象：

- **Source**：适中长度的原始证据文本。Episode 通过 `source_id` 回到原文。
- **Episode**：可以独立理解的一段事件、状态、立场或对话事实，是主要检索单位。
- **Concept**：人物、组织、地点、物品、情绪、抽象概念等可被联想的语义节点。
- **Association**：Episode/Concept 之间的有向关系。推断边另外记录 `generation`，表示它距离直接证据经过了多少代推断。

所有持久化和内存 embedding 当前统一使用 `float32`。本阶段没有重新引入 float8/float16，也没有把 Paragraph 作为正式检索层。

## 3. 评测术语

### 3.1 事实槽（fact slot）

一个问题可能要求回答多个彼此独立的事实。例如“谁建立了某组织，以及依据什么权限”至少有“宣告者”和“权限来源”两个槽。只有每个必需槽都找到证据，整题才算完整通过。

### 3.2 Oracle / 证据答案集合

评测为每个事实槽保存一组允许命中的 Episode ID。这组集合不是模型答案，而是人工可审计的证据标准。只要最终证据命中其中任一等价 Episode，该槽就通过。

### 3.3 Candidate@100

混合检索产生的前 100 个候选 Episode。它衡量基础召回是否把正确证据送到了后续阶段。若正确证据不在 Candidate@100，后面的 LLM 重排再聪明也无法恢复。

### 3.4 最终证据（final evidence）

经过稀疏检索、向量检索、图扩展、来源队列和 LLM 重排后，实际交给回答模型的证据集合。最终事实槽召回比 Candidate@100 更严格。

### 3.5 结构化查询与 `__answer_slot__`

结构化查询不是向问题硬编码答案，而是明确描述“还缺哪一种证据”。例如：

```text
__answer_slot__ 某组织由谁宣告或建立，权限依据是什么
```

它让稀疏检索优先寻找“建立者 + 权限来源”，同时避免因为问题正文只出现“组织成立”而把宣言内容误当成权限证据。

### 3.6 确定性证据保护（evidence floor）

LLM 重排具有随机波动。若一个结构化答案槽通过稀疏检索获得了非常明确的高排名证据，系统会为它保留最低证据席位，防止重排器把整个槽删掉。这不是强行指定某个剧情答案，而是保护已经由独立检索通道证明高度相关的候选。

### 3.7 追问规划（follow-up planning）

在首次意图解析后，额外调用一次 LLM 生成补充查询。例如问题后半段用了“这名少女”，而她是谁必须由前一跳回答，追问规划器可生成包含真实实体的第二轮检索词。

### 3.8 冻结计划 A/B 与动态验证

- **冻结计划 A/B**：复用同一份意图解析结果，只改变是否执行追问。优点是变量单一；缺点是不能观察意图解析本身的随机波动。
- **动态验证**：重新调用模型解析意图，更接近真实运行，但不同运行之间不再完全同构。

两者必须结合使用，不能用冻结 A/B 单独证明线上稳定性。

## 4. 扩展测试集设计

扩展清单包含 15 个动态问题、57 个必需事实槽和 152 个唯一证据 Episode。问题覆盖：

- 同一卷内远距离跨文件因果链。
- 人物、组织、代号和别名的多跳映射。
- 哲学概念在不同人物动机中的投影。
- 行动执行者、幕后协助者和更早动机的回溯。
- 同一概念在多个立场中的对照。
- 宣告者、制度权限和事件后果的分离证明。

扩展清单使用可审计的导入机制复用已有题库，并允许显式记录：

- `group_alternative_additions`：补充等价证据。
- `group_alternative_overrides`：替换被确认错误的证据集合。
- `group_required_source_additions`：补充允许的来源文件。

校验器会检查空证据槽、数据库中不存在的 Episode、来源越界和导入解析错误。当前清单离线校验全部通过。

## 10. 当前自适应追问策略

前台公共知识检索默认使用 `entity_resolved` 模式；后台增长仍使用 `always`，避免前台延迟优化改变后台建边语义。

规则如下：

1. 若问题包含答案依赖的后续指代，例如“是谁……这名少女又喜欢什么”，调用规划器。
2. 若意图解析生成至少 12 条搜索查询，调用规划器作为复杂问题安全网。
3. 若问题中的实体和关系都已经被初始查询明确命名，跳过规划器。

## 11. 当前结论的证据等级

### 已经直接证明

- 15 题扩展清单本身有效，57 个槽均有存在于数据库且来源合法的证据。
- 初始完整基线为 11/15、53/57。
- 修正评测资产后，同一结果为 13/15、55/57。
- 两个真实失败分别在线重跑后通过。
- 自适应跳过路径至少在 `concept_bridge_04` 上真实通过，并显著省去规划耗时。
- 高复杂度安全网能恢复日富美/梓题的权限槽。
- 当前代码的 168 项引擎测试和 22 项聊天机器人集成测试全部通过。

### 只有组合证据，尚未证明稳定性

- 把修正后的旧基线与两个定向重跑合并，可以得到 15/15、57/57。
- 但这不是一次全新、同一版本、同一运行条件下的 15 题完整重跑。
- 因为 LLM 意图解析和重排存在随机性，不能据此宣称系统已稳定达到 100%。

### 仍未证明

- 多次重复运行后的置信区间和最差情况。
- 自适应策略在更大、更多语言的问题集上没有召回回退。
- 新增长 Association 相对于纯基础检索的稳定净收益。
- 当前 57 槽是否足以代表将来所有用户记忆问题。

## 14. 当前最重要的技术问题

### 14.1 LLM 重排成本已经占主导

最新跳过追问的查询中，37.716/52.161 秒花在证据重排。继续优化 SQLite、NumPy 或追问规划，不会解决最大延迟。

### 14.2 意图解析存在运行间波动

同一类复杂问题可能某次生成完整查询，另一次漏掉权限或因果维度。结构化答案槽能减少风险，但不能穷举所有自然语言问法。

### 14.3 事实完整性与证据数量不同

增加候选或最终证据数量不保证覆盖更多事实槽。系统必须针对“问题要求的答案维度”做覆盖，而不是单纯扩 Top-K。

### 14.4 Oracle 维护本身是实验风险

当正确证据集合不完整时，系统改善可能被误判为失败。以后每个新失败都应先做“证据标准审计”，再改检索器。

## 15. 建议的下一阶段路线

优先目标应从“继续生成更多查询”转为“在保持事实槽召回的前提下，减少送入 LLM 重排的文本”。

### 阶段 A：确定性预压缩

1. 保留 Candidate@100 作为高召回池。
2. 按结构化答案槽、来源文件、实体覆盖和稀疏/向量排名做确定性分层。
3. 每个答案槽至少保留若干候选，再把候选压缩到 30–50 条交给 LLM。
4. 记录被删除候选的原因，保证可回放。

### 阶段 B：受控 A/B

比较：

- 当前 100 候选直接重排。
- 50 候选预压缩后重排。
- 30 候选预压缩后重排。

核心指标是 Candidate 槽召回、最终槽召回、完整问题率、LLM 输入 token 和各阶段耗时。边数量不作为评测指标。

### 阶段 C：全量稳定性验证

选出不回退的压缩配置后：

1. 对 15 题进行同版本完整重跑。
2. 至少重复 3 次，报告平均值、最差值和每槽失败频率。
3. 对失败运行保存完整意图、候选、重排输入输出和证据来源。

### 阶段 D：再评估增长边收益

基础检索稳定后，再用同一批问题比较：

- 禁用增长边。
- 只使用 generation=0 的直接关系。
- 允许 generation=1。
- 允许更高 generation，但降低权重并标明推断距离。

这样才能区分“基础召回改善”和“新 Association 真正带来的新证据路径”。

## 16. 最终判断

本阶段最有价值的结果不是某个单次 100% 数字，而是建立了可审计的诊断闭环：

```text
问题拆成事实槽
→ 检查正确证据是否进入 Candidate@100
→ 检查是否被 LLM 重排删除
→ 区分 Oracle 错误与系统错误
→ 用结构化答案槽修复特定缺口
→ 用动态运行验证模型波动
```

当前基础召回已经接近可用，但稳定性仍受 LLM 意图解析与大候选重排影响。下一步最值得投入的是“答案槽感知的确定性预压缩”，而不是继续扩大无条件追问或盲目增加 Top-K。
