# 前台证据预压缩实验报告

日期：2026-08-30  
实现版本：`v3.39_slot_aware_precompression`  
评测对象：公共剧情知识库前台检索  
正式配置：Candidate@100，确定性压缩至64条后进入LLM证据重排

## 1. 目标

上一阶段确认了前台查询的主要瓶颈已经不是SQLite、NumPy向量检索或图扩展，而是LLM证据重排。典型查询中，重排会读取100个Episode，占全流程一半以上时间，并消耗大量输入token。

本阶段的目标不是缩小基础召回池，而是分离两个概念：

```text
Candidate@100
    保持不变，用于高召回

LLM rerank input
    在Candidate@100内部做确定性预压缩
```

因此即使压缩策略失败，日志中仍然保留完整Candidate@100，可以明确判断正确证据是在基础检索中缺失，还是被预压缩错误删除。

## 2. 专有名词

### Candidate@100

稀疏检索、向量检索、Source扩展、Concept/Association图扩展等通道合并后的100个Episode候选。它是高召回池，不直接等于最终回答证据。

### 预压缩（precompression）

在调用LLM重排之前，用纯程序规则把Candidate@100缩小到固定预算。预压缩不调用模型，不生成新事实，也不改变数据库。

### 重排输入（rerank input）

实际发送给LLM证据覆盖侦察器的Episode集合。本阶段测试了100、50、30和64条预算。

### required evidence floor

由结构化答案槽、严格约束槽和局部相邻证据确定的最低保护集合。这些证据会优先进入重排输入，避免LLM之前的压缩把某个明确答案维度整体删除。

### atomic anchor

每个原子查询分别召回的高排名Episode。不同查询的锚点采用轮询交错，防止一个宽泛子问题占满全部候选预算。

### fact slot

问题中必须独立证明的事实维度。15道扩展题共有57个事实槽。一道题只有所有必需槽都命中才算完整通过。

## 3. 预压缩算法

预压缩器完全确定性运行，规则为：

1. 保留Candidate@100的完整、有序ID列表作为审计资产。
2. 优先加入required evidence floor。
3. 其余位置按原有候选池顺序填充。
4. 原有候选池已经按“一条全局候选、两条原子锚点”交错，因此继续保留全局相关性与答案槽覆盖的平衡。
5. 每个候选记录：Candidate排名、是否保留、保留或删除原因。

原因类型包括：

- `required_evidence_floor`
- `atomic_anchor`
- `global_rank`
- `dropped_budget`

默认值为100时算法是严格no-op，候选顺序不变，保持向后兼容。

## 4. 评测方法

本阶段使用15道扩展问题、57个事实槽。

为了减少无关随机变量，A/B工具冻结已有的LLM意图解析结果和追问查询，只改变进入证据重排器的候选预算。每次运行同时测量：

- Candidate@100事实槽召回。
- 预压缩后重排输入事实槽召回。
- 最终证据事实槽召回。
- 候选正文字符数。
- 初始重排提示词字符数。
- API返回的真实prompt/completion token。
- 证据重排阶段耗时和总耗时。

Association增长在全部实验中关闭，正式剧情数据库只读。

## 5. 实验中发现的冻结意图缺陷

第一轮三题A/B报告：

`logs/foreground-precompression-ab/20260830T000304.396840Z/report.json`

第一轮显示50和30条预算漏掉多个事实，但审计发现冻结意图来自旧版本；`intent_override`路径直接使用旧搜索查询，绕过了当前版本后来新增的结构化答案槽。

这不是预压缩算法本身的有效失败，而是实验控制路径与生产路径不一致。

修复后规则为：

- 动态意图与`intent_override`都追加当前确定性结构化答案槽，并去重。
- 只有完整`frozen_plan`保持字节级冻结，不追加新策略。

这保证“冻结随机LLM意图”不等于“冻结旧版确定性检索策略”。

## 7. 50条预算扩大到完整15题范围

前三题报告同上；剩余12题报告：

`logs/foreground-precompression-ab/20260830T002052.562424Z/report.json`

合并结果：

| 层级 | 完整问题 | 事实槽 |
|---|---:|---:|
| Candidate@100 | 15/15 | 57/57 |
| 重排输入@50 | 14/15 | 56/57 |
| 最终证据 | 14/15 | 55/57 |

唯一被50条预压缩删除的事实槽来自：

`old_cathedral_symbol_infrastructure_and_limits`

缺失内容是“阿里乌斯小队的导弹与突入部署”。等价证据Episode 1518在Candidate@100中排名第51，仅比预算边界晚一位。

另一个最终缺失槽“伊甸条约旨在避免圣三一与格黑娜全面战争”的Episode 304已经存在于50条重排输入中，是LLM最终选择波动，不是预压缩失败。

结论：50条对包含8个独立事实槽的长复合问题缺少安全余量，不能设为默认。

## 8. 64条预算完整15题验证

完整报告：

`logs/foreground-precompression-ab/20260830T003228.613191Z/report.json`

| 层级 | 完整问题 | 事实槽 | 召回率 |
|---|---:|---:|---:|
| Candidate@100 | 15/15 | 57/57 | 100% |
| 重排输入@64 | 15/15 | 57/57 | 100% |
| 最终证据 | 15/15 | 57/57 | 100% |

平均指标：

- 重排输入Episode：64。
- 候选正文字符：4,751.7。
- 初始重排提示词字符：20,357.2。
- 总耗时：40.783秒。
- 证据重排耗时：35.795秒。
- 15题证据侦察prompt token：154,584。
- 1次额外短名单压缩prompt token：6,549。
- 总重排prompt token：161,133，平均每题10,742。
- 总重排completion token：11,058，平均每题737。

为了避免拿不同题目构成的平均值直接比较，又单独抽取与100条对照相同的三题：

| 指标 | 100条 | 64条 | 变化 |
|---|---:|---:|---:|
| 候选正文字符 | 7,934.7 | 4,889.0 | -38.4% |
| 初始提示词字符 | 32,399.3 | 21,189.7 | -34.6% |
| 重排prompt token | 47,997 | 32,901 | -31.5% |
| 总耗时 | 59.642秒 | 57.802秒 | -3.1% |
| 重排耗时 | 52.628秒 | 50.575秒 | -3.9% |

输入token下降是直接、可重复计算的；单轮时延只下降约3%，说明当前服务端排队、模型思考和输出长度波动远大于输入缩短带来的延迟收益。不能宣称时延按token比例下降。

## 9. 最终配置决策

聊天机器人前台：

```text
Candidate pool       = 100
LLM rerank input     = 64
final evidence limit = 原配置不变
```

引擎通用默认与后台增长任务继续使用100条：

- 前台目标是低token、可接受延迟和稳定证据覆盖。
- 后台/深度任务不在用户回复关键路径上，优先保守可靠。
- 环境变量可以立即把前台恢复为100，不需要改代码。

配置项：

```text
MEMORY_FOREGROUND_RERANK_PRECOMPRESSION_LIMIT=64
```

## 12. 局限与下一步

本阶段64条结果是一轮完整15题运行，强于此前的定向组合证据，但仍只有一次重复。它证明当前样本上没有观察到召回损失，尚不能证明长期概率为零。

下一步建议：

1. 使用64条配置对15题至少再重复2轮，获得每槽失败频率。
2. 将新用户记忆问题逐步加入独立测试集，避免只对剧情长问题优化。
3. 继续记录真实API usage；token是主要收益指标，时延作为受服务端波动影响的次要指标。
4. 若未来出现Candidate排名64以后才有唯一正确证据，优先改进答案槽召回与floor，而不是无限扩大固定预算。
5. 在基础检索稳定后，再重新评估generation不同的增长边是否带来额外证据路径。

## 13. 结论

64是当前数据支持的最小可靠默认值：

- 30明确失败。
- 50在高槽位复合题上失败。
- 64在完整15题、57槽上同时保持Candidate、重排输入和最终证据100%命中。
- 与相同三题的100条对照相比，真实重排prompt token减少31.5%。

因此本阶段达成了“保持Candidate@100基础可靠性，同时减少进入LLM的证据量”的目标，但时延收益仍需多轮测量。
