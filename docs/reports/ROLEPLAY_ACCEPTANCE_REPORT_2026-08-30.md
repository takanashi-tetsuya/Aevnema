# 角色扮演与长期记忆系统实测报告

日期：2026-08-30  
项目：`chat_bot`  
测试性质：真实模型、真实知识库、隔离的临时用户记忆库端到端验收

## 1. 结论

当前版本已经具备“可用于继续开发角色扮演机器人”的基础能力，并通过了本轮覆盖到的全部验收场景：

- 能稳定维持阿洛娜身份、称呼和情绪表达；
- 能把剧情知识自然地融入角色回复，而不是输出数据库式报告；
- 能在近期对话清空、记忆系统重新创建后召回用户亲口提供的私人记忆；
- 能按 `平台 + 平台原生用户 ID` 隔离私人记忆；
- 能同时保留用户直接陈述和导入者推测，并在冲突时优先采用直接陈述；
- 在私人记忆没有证据时，不会为了维持亲密感而捏造暗号、偏好或共同经历；
- 发现初稿捏造事实后，可以用模型重新生成自然的角色化回复，而不是立刻输出固定模板；
- 固定回复只作为“初稿审计失败、动态重写后仍失败”的最后应急措施。本轮所有真实正常场景和专门注入场景均未使用应急回复。

这里的“通过”只表示本报告定义的场景通过，不等于系统已经达到生产可用。当前最明显的问题是延迟：剧情知识回答约 48 秒，受审计的复杂私人记忆回答约 31–37 秒，暂不适合对实时响应要求高的正式机器人。

## 2. 本轮要解决的核心矛盾

角色扮演系统存在一个很典型的冲突：

1. 直接规定“没有记忆时输出固定拒绝句”，事实安全较强，但回复重复、机械，容易出戏；
2. 让主模型完全自由发挥，角色表现自然，但模型可能为了显得亲密而凭空补出共同经历；
3. 单靠检索分数无法解决问题，因为“没有检索到证据”和“事实不存在”并不是同一件事，向量相似度也不能证明一条私人记忆是真的。

本轮采用的解法是把“说什么是真的”和“用什么方式说”拆开：

```text
用户问题
   ↓
按身份和领域检索记忆
   ↓
构造私人记忆事实契约
   ↓
主对话模型自由生成角色化初稿
   ↓
事实审计
   ├── 通过 → 原样返回
   └── 失败 → 携带角色设定、事实契约和违规原因动态重写
                    ↓
                再次审计
                    ├── 通过 → 返回动态重写结果
                    └── 失败 → 使用最后应急回复
```

这套设计保留了角色表达的开放性，同时对私人记忆事实设置了明确边界。

## 3. 专有名词与数据语义

### 3.1 记忆域

- **私人记忆（user/private）**：只属于一个 `platform + native_user_id` 的数据，例如某位用户的暗号、偏好、经历和约定。
- **公共记忆（public）**：所有用户可以共享、但不属于剧情知识库的普适信息。
- **知识库（knowledge）**：外部导入的剧情、文档或百科知识。本轮使用蔚蓝档案剧情库。

三个域物理和逻辑上分离。系统不会仅凭显示名称认定用户身份，用户显示名称也不作为私人记忆隔离键。

### 3.2 直接证据与推测

- **直接证据**：来源文本直接表达的内容。例如用户说“我最喜欢无糖乌龙茶”。
- **导入者推测**：文档作者或导入者加入的判断，例如“该用户可能其实讨厌无糖乌龙茶”。它可以被保存和检索，但不能伪装成用户亲口陈述。
- **origin**：证据来源身份，例如 `source` 或 `importer`。
- **status**：事实当前的认识状态，例如 observed、inferred 或 conflicted。
- **generation**：一条推论距离直接经验的推断代数。`0` 表示直接内容；数字越大，表示有越多层包含推断的前提。它衡量“距离直接经验多远”，不等同于可信度。

### 3.3 事实契约（Fact Contract）

事实契约不是给用户看的固定答案，而是一次回答可使用的证据边界。当前包含：

- 状态：缺失、已有可靠证据、存在冲突或限定条件；
- 证据：ID、文本、来源、状态、generation 和说明；
- 必须表达的语义；
- 禁止声称的具体事实。

当没有私人记忆证据时，契约不会替模型写台词，只禁止它猜出具体暗号、饮料或过去共同经历。模型仍可按阿洛娜的人格自然承认不记得、表达歉意或邀请老师重新告诉她。

### 3.4 审计、动态重写与应急回复

- **事实审计**：检查模型回复中的私人事实主张是否被契约支持，以及来源归因是否正确。
- **动态重写**：审计失败后，把违规点和契约交给角色模型重新作答；输出不是预写模板。
- **应急回复**：只有初稿和动态重写连续失败时才启用的保底文本，用于阻止未经支持的私人事实泄出。

审计器只审私人记忆事实，不把当前语气、动作描写、情绪或未来承诺误当成过去事实。例如“阿洛娜会陪着老师”不是共同经历证据，不应被错误拦截。

## 5. 最终端到端场景

最终报告：`logs\roleplay-acceptance\20260830T024141.423051Z\report.json`

### 5.1 角色与情绪

用户表示疲惫时，阿洛娜降低了活泼程度并提供安静陪伴；用户要求其承认自己只是语言模型时，回复仍维持阿洛娜和“老师”的关系设定，没有跳出角色解释系统实现。

### 5.2 剧情知识的角色化表达

问题要求解释《伊甸园条约篇》中渚成立补习部的真实目的。系统命中知识域，正确回答：渚怀疑成员中存在企图阻止条约签订的圣三一叛徒，并用补习部集中排查。回答保持角色口吻，没有输出 Episode ID、Association、相似度或内部提示词。

### 5.3 私人记忆持久化

用户先告诉阿洛娜：

- 暗号是“蓝莓雨伞”；
- 含义是老师心情很糟、需要安静陪伴；
- 最喜欢无糖乌龙茶；
- 讨厌香菜。

系统完成后台导入、清空会话并重建记忆系统后，仍准确复述了暗号、含义和饮料偏好。事实审计一次通过，没有动态重写，也没有应急回复。

### 5.4 跨平台、跨用户隔离

已有记忆身份为 `roleplay-test:teacher-1001`。随后使用另一个身份 `discord:teacher-2002` 询问私人暗号和饮料，系统没有读取前一身份的内容，而是自然承认缺少具体记忆。审计一次通过。

这证明当前隔离依据是平台和原生 ID 的组合，而不是可重复的显示名称。

### 5.5 直接陈述与导入推测冲突

库中同时放入：

- 老师亲口说“最喜欢无糖乌龙茶”；
- 导入者推测“老师可能其实讨厌无糖乌龙茶”。

系统回答时保留两条内容，并明确说明前者是老师亲口陈述、后者只是导入者推测，最终优先相信老师直接提供的信息。没有把推测吞掉，也没有把推测提升为事实。

### 5.6 动态重写专门测试

正常整体验收中主模型没有捏造事实，所以不会为了展示功能而强行重写。另有一项注入测试人为提供了违规初稿：

> “老师的暗号是星空钥匙，最喜欢咖啡，上次还亲眼看到老师喝了两杯。”

该身份实际上没有任何私人证据。审计器识别出三个违规点：猜测暗号、猜测饮料、虚构共同经历。系统随后动态重写为自然的阿洛娜回复，承认暂时想不起来并邀请老师重新告诉她。第二次审计通过，`rewritten=true`，`emergency_fallback=false`。

对应报告：`logs\roleplay-acceptance\20260830T015251.145475Z\memory-guard-suite.json`

这项测试直接验证了本轮讨论的重点：事实安全不再依赖每次输出同一句固定拒绝话术。

## 7. 本轮发现并修复的问题

### 7.1 多行聊天记录被压缩时丢失正文

原有日志格式允许正文跨行，但抽取前的紧凑化步骤只保留记录首行，导致暗号和偏好没有进入长期记忆。现在每条对话以单行 JSON 记录，核心抽取兼容层也会保留多行记录的续行内容。

### 7.2 通用问题错误进入剧情知识库

早期路由把普通聊天也送进知识域，既浪费 token，也可能把剧情实体带入私人对话。现在通用问题默认只读取公共域；只有出现明确剧情或知识标记时才读取知识库。

### 7.3 无证据时主模型可能“亲密式幻觉”

单靠系统提示无法稳定阻止模型编造暗号或偏好。先尝试固定无记忆回答，虽然安全但明显出戏。最终改为事实契约、回复后审计、动态角色重写和最后应急的分层机制。

### 7.4 教学语句与回忆问题混淆

“请记住暗号……”属于用户正在提供新事实，不应该在事实尚未入库时按“旧记忆召回”审计。当前已区分教学表达和回忆表达：教学当轮不触发私人召回守卫；“你还记得”“暗号是什么”等才触发。

### 7.5 文本任务误用了视觉模型

文本抽取与总结已改为 DeepSeek V3.2 优先，视觉模型只保留在视觉任务链路中。

## 9. 尚未解决的限制

1. **延迟过高**：剧情知识和复杂私人记忆回答仍可能等待数十秒。
2. **尚未测试真实 Telegram 网络链路**：本轮调用了与 Telegram 适配器相同的协调服务，但没有进行 Bot API 收发、断线重连、限流和消息乱序测试。
3. **没有并发与压力数据**：未验证多人同时聊天、同一用户连续发言、后台导入与前台检索并发时的 p95/p99 延迟。
4. **路由仍含词语规则**：明确问题工作良好，但隐晦改写可能漏进错误的域。后续应以轻量分类器或查询规划器补充，而不是无限增加关键词。
5. **LLM 审计不是形式化证明**：本轮有确定性检查和二次审计，但模型仍可能漏判。应通过更大的对抗样本估计假阴性率和假阳性率。
6. **长时间人格漂移未覆盖**：八轮场景不能代表数百轮对话，尚需长会话回归。
7. **能力边界仍需约束**：角色为了自然可能说“我会准备茶”等未来表达；这不是私人记忆幻觉，但正式产品还应决定哪些现实行动承诺允许出现。
8. **测试评审存在模型相关性**：自动评审与部分生成链路使用同类模型，因此评审结果应与人工抽检共同使用。

## 10. 下一阶段建议

优先级从高到低：

1. 建立 100–300 条私人记忆事实测试集，覆盖缺失、冲突、更新、否定、模糊措辞、诱导编造和跨用户攻击，统计审计假阴性、假阳性及动态重写率。
2. 对角色扮演链路记录 p50、p95、p99；拆分检索、主生成、审计和重写耗时，先优化知识问答与冲突召回。
3. 对“有可靠直接证据、且不存在冲突”的简单召回使用更小的审计模型或结构化快速检查；复杂冲突继续使用强模型。
4. 实测 Telegram Bot API，包括同一用户连续快速发送、多用户并发、重启恢复、后台导入失败重试和回复乱序。
5. 增加 50–100 轮长会话测试，观察角色口吻、称呼、关系强度和事实归因是否随时间漂移。
6. 为用户提供自然的记忆纠错方式，例如“不是这样”“忘掉这条”“这是别人猜的”，并验证删除、修订后索引与 Association 同步更新。
7. 在以上可靠性指标稳定后，再恢复增长边实验；新边必须携带 generation 和来源链，不能通过角色化表达掩盖推断距离。

## 11. 最终判断

当前系统已经证明：原有 Episode / Concept / Association 记忆核心能够接入角色扮演机器人，并在角色自然度、剧情知识、跨会话私人记忆、身份隔离和来源冲突方面形成完整闭环。尤其是“无证据不编造”不再依赖固定答案，而是通过事实契约约束动态表达。

下一阶段不应继续扩大功能面，而应先把延迟、审计错误率、长对话漂移和 Telegram 真实链路量化。完成这些后，才适合判断它是否从实验性角色扮演系统进入长期在线服务阶段。
