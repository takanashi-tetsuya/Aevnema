# 记忆系统接入角色扮演聊天：阶段实验报告

日期：2026-08-30  
范围：`chat_bot` 与关联记忆引擎的简单剧情问答、创造性角色扮演、私人记忆隔离、回答后剧情增长。

## 1. 本阶段要回答的问题

本阶段不是再次验证复杂多跳剧情问答，而是验证记忆系统进入实际聊天后能否同时满足四项要求：

1. 用户没有明确说“请查询剧情”时，系统仍能识别人物、地点和隐含背景需求。
2. 当前任务、学生新消息等创造性内容可以自然生成，并进入当前用户的私人记忆。
3. 创造性内容不能污染原作剧情库，但回答中真正有价值的剧情推论仍有机会形成新的 Association。
4. 简单会话尽量在五秒内回复，深层增长在后台完成。

## 2. 术语与数据边界

### 2.1 Source、Episode、Concept、Association

- **Source**：可追溯的原始材料。剧情文件和一批完整对话都先作为 Source 保存。
- **Episode**：可以独立理解的一段事件或状态记忆。
- **Concept**：人物、地点、组织、抽象情绪、行为倾向等可联想节点。
- **Association**：Episode/Concept 之间有方向、权重、关系文本和证据的连接。

### 2.2 三个记忆域

- **剧情知识域（knowledge）**：所有用户共享的原作材料和经过审计的稳定剧情推论。
- **公共域（public）**：所有用户可共享，但不属于某个原作知识库的内容。
- **用户域（user）**：由“平台 + 平台原生用户 ID”隔离的私人记忆。显示名不参与身份唯一性。

### 2.3 confidence 与 generation

- **confidence** 表示一条命题或关系本身有多可信。
- **generation** 表示它离直接材料有多少层推断。`generation=0` 是直接材料；数字越大，表示越多次以推断为前提继续推断。
- 两者不能互相替代。高置信度的多代推论仍然比直接材料离证据更远。

### 2.4 evidence-gated growth

“证据门控增长”不是把剧情库设为只读。它表示：

1. 同一次聊天回复可以提出一个新的稳定剧情候选。
2. 候选必须列出两个本轮实际检索到、且彼此不同的 Episode ID。
3. 程序本地确认 ID 确实可见，模型不能伪造证据编号。
4. 程序先拒绝直接事实复述、低于 0.72 的低置信候选、未知关系类型和含多个命题的复合候选。
5. 合格候选固定这两个端点，依次经过 Qwen 主审、DeepSeek 对抗终审和确定性完整性检查；任何一层拒绝都不写入。
6. 回答衍生候选不再重新执行整条宽检索流程，也不以“同一问题立即提高召回”作为写入前提；其效用由后续隔离 A/B 验证。自主探索式增长仍保留反事实效用门。
7. 当前任务、刚收到的消息、当前用户互动只进入用户域。

## 3. 最终实现路线

### 3.1 同一次模型调用生成可见回答和隐藏候选

旧路线是“生成回答后，再调用一个模型拆分命题”。实测中，这个额外调用单次可超过 90 秒，且重复发送问题、回答和证据，既慢又没有必要。

现在由同一次聊天调用先输出一个短机器块，再输出自然回答：

```text
<assistant_memory>{"k":[...],"p":[...]}</assistant_memory>
给老师看的自然回答
```

- `k` 是最多一条稳定剧情推论，必须引用可见 Episode。
- `p` 是当前用户的临时任务、消息或互动。
- 程序在本地移除机器块，用户、会话窗口和对话日志都只看到自然回答。
- JSON 损坏、没有前提、引用不存在的 Episode 时，剧情写入默认关闭。
- 私人记忆保护器若重写了回答，原草稿对应的候选全部作废。

### 3.2 创造性回合使用独立上下文视图

历史 Episode 对事实问答是证据，但对“现在有哪些消息”很危险：模型可能把过去剧情原样说成刚发生的消息。

因此当前任务/消息类请求使用：

```text
用户私人 Episode 正文
+
公共记忆正文
+
剧情 Concept 名称与简短描述
```

不向这类生成请求展示剧情 Episode 正文。普通“我要去阿拜多斯出差”仍可使用完整静态背景；只有明确创建当前任务、消息、日程时才切换视图。

创造性追问会携带最近的用户陈述，但不会把助手上一轮创造的内容作为检索查询前提。助手的可见会话历史仍可保证叙事连续性，最终内容再通过对话 Source 进入私人记忆。

### 3.3 前台与后台模型分工

- 简单聊天：`Qwen/Qwen3.5-35B-A3B`，关闭 thinking，`max_tokens=260`。
- 用户对话入库：同一 Qwen 模型，关闭 thinking，`max_tokens=2400`，lean 导入配置。
- 剧情增长：Qwen 负责检索、关系草案和主审；`DeepSeek-V3.2` 保留为独立对抗终审。
- 剧情候选增长最多一轮，并恢复“只持久化实际有用关系”的效用门。
- 回答后已经给出固定 Episode 端点的候选走直接审计通道，跳过关系重新生成和宽检索；成功或正在处理的候选按“推论文本 + 前提 Episode + 类型”持久去重。

底层记忆客户端已新增 `reasoning_max_tokens` 和 `reasoning_enable_thinking`，因此这些限制不是只存在于聊天层。

## 4. 实测数据

所有增长写入都在正式剧情数据库的副本中完成，正式库没有新增或改写 Source、Episode、Concept、Association。早期多边 A/B 的基线检索曾直接读取正式库，而检索器会顺带更新 Association 的 `use_count/last_used`，因此它触碰了使用统计；后续已改为基线、实验组各自使用全新副本，并加入正式库运行前后签名检查。最终严格隔离实验中正式库完全未变化。

最终前台实验中：

- 直接剧情问答：6.87 秒，其中检索 3.92 秒、生成 2.93 秒。
- 间接人物评价：4.14 秒。
- 隐含出差背景：4.17 秒。
- 创造任务：4.18 秒。
- 创造消息：3.78 秒。

结论是：简单创造性角色扮演已大多进入五秒，但多事实槽的直接剧情问答仍不稳定；当前不能宣称“所有简单会话稳定低于五秒”。

## 5. 已验证的结果

### 5.1 剧情问答和间接背景调用

“白子喜欢什么活动，以及老师成为支持者后的反应”能够准确命中公路自行车、支持者、第一次被认真支持和心跳反应。  
“你觉得白子是什么样的人”能够在没有直接要求查询的情况下，结合骑行习惯、技术态度和被支持时的反应形成自然人物评价。

### 5.2 当前创造内容的私人隔离

完整实验生成并导入了：

- 1 个私人 Source
- 5 个私人 Episode
- 9 个 Concept（full-02）/相近规模的后续实验结果
- 17—28 条私人 Association

任务与消息原文可从私人 Source 无损恢复；重新进行仅用户域检索时，可以命中“出差、任务、消息、学生”等本轮内容。私人 Episode 被标为 `mixed/reported` 或相应系统生成边界，`generation=1`，没有冒充用户直接经验。

### 5.3 剧情污染防护

所有实验中，角色扮演都没有向正式剧情库增加 Source、Episode、Concept 或 Association。早期多边 A/B 曾更新既有 Association 的使用次数和最近使用时间；这不改变剧情内容，却仍属于不必要的正式库写入，现已修复为双副本实验。正式库当前仍为 736 个 Source、4073 个 Episode、8904 条 Association，最大 Association ID 为 8904，不含实验边 8905—8908。  
宽松增长实验虽然新增 8 条 Association，但其中涉及普通白子与另一形态白子的跨节点扩展，说明“通过双审计”仍不等于“在当前候选范围内有必要”。  
恢复效用门并限制一轮后，同类两个候选最终新增 0 条边，证明安全门能够阻止无效扩张。

### 5.4 本地回归

- chatbot：58 项通过，其中包含 A/B 数据库隔离、`MEMORY_RERANKER_MODEL` 空值关闭全部检索重排、light/standard/deep 路由、完整重度参数切换、异常恢复、取消等待，以及 Windows/WSL 绝对路径互转回归。
- 底层记忆系统：187 项全部通过；其中包含专用 reranker 请求解析、返回顺序/分数校验、cross-encoder 后端跳过 LLM 审查，以及原有查询、增长、证据选择和 provenance 回归。
- chatbot 配置回归还验证了前台可选择 `cross_encoder`，后台增长与深度审计仍固定使用 `llm`，不会因前台加速开关而失去语义审计。

## 6. 尚未解决的问题

### 6.1 五秒目标不稳定

最终简单创造性回合已经达到 3.78—4.18 秒，但直接剧情问答仍为 6.87 秒。剩余主要成本在轻量检索，而不是回答生成。创造性回合从最多 7 个向量子查询压缩为 1 个后，检索下降到约 2.4—2.8 秒；直接事实问答仍保留多槽查询，以免牺牲召回可靠性。

下一步应测试：

1. query embedding 的短期缓存；
2. 同一轮多个事实槽的 embedding 批量请求和去重；
3. 首轮检索已高置信命中时跳过低收益槽；
4. 分别统计网络 embedding、NumPy 搜索、SQLite 精排和图扩展耗时。

### 6.2 回答后增长已从单例推进到冻结多边 A/B

本节术语含义如下：

- **候选边**：回答模型基于两个已经展示给它的 Episode 提出的关系；它只是待审命题，不是证据。
- **固定端点**：审计只能检查候选指定的两个 Episode，不允许偷偷改搜到更容易成立的邻近节点。
- **双审计**：Qwen 主审判断关系是否成立，DeepSeek 以反方视角检查越界补全；二者都接受才可写入。
- **generation**：关系离直接文本证据的推断代数。此次新边以两个 generation 0 Episode 为前提，因此写为 generation 1。
- **路径收益**：检索结果实际携带新 Association，给回答模型提供“两个证据为何相关”的可追溯解释。
- **召回覆盖收益**：基线漏掉两个前提之一，而实验组沿新边补回缺失 Episode。基线已经召回两端时，不能再凭空增加覆盖，此时只考察路径收益。

首先完成的单边闭环使用 Episode 1166 与 1361，形成“未花的合作设想与阿里乌斯实际执行目标存在失控性反差”的 `semantic/thematic_contrast` 边。双审计接受，`generation=1`，跨重启重复写入被拦截。三题 A/B 中 3/3 使用新路径，1/3 补回一个缺失前提，总前提命中净增 1、零回退。

随后冻结 6 个候选和每个候选 3 个问题，再开始模型审计，避免根据结果修改题目。最终真实审计耗时 38.984 秒，4/6 候选通过并写入隔离副本：

1. 未花的合作设想与阿里乌斯实际目标：`contrast`，通过。
2. 补习部的考试表象与政治用途：`contrast`，通过。
3. 未花对格黑娜的敌意如何推动政变：`motivation`，通过。
4. 渚对日富美的怀疑与浮士德身份之间的“部分解释但不能证明叛徒”关系：`contrast`，通过。
5. 日富美＝浮士德候选：拒绝。身份本身有证据，但候选后半句增加了“用该身份证明自己能站在梓身边”的心理目的，两个固定端点不支持。
6. 乐园悖论映射到人际信任候选：拒绝。两个端点分别包含悖论和老师选择相信学生，但没有直接支持“剧情把不可证明性投射为人际信任机制”这一主题升级。

审计过程中还发现了一处关系建模错误：原实现会把回答产生的 `identity` 候选映射为 Episode→Episode 的 `identity/same_identity`，等于声称“两段剧情是同一事件”。现在改为 `semantic/identity_evidence`：两个 Episode 只作为人物别名/身份结论的证据；真正的同事件判断继续保留严格审计，未被放宽。

对 4 条通过边执行 12 题严格隔离 A/B，最终结果为：

- 4/4 条边都在至少两个对应问题中提供路径收益。
- 12 题中 9 题实际使用新边；其余 3 题没有被相关性门强行塞入边。
- 2/4 条边各在一题中补回 1 个基线遗漏 Episode；总前提召回净增 2。
- 12 题中目标前提召回回退为 0；新边没有挤掉本来命中的目标证据。
- 平均基线检索为 4.351 秒，实验组为 3.426 秒。两组虽从同一正式库分别复制并并发执行，但样本仅 12 题，网络、缓存和调度噪声足以造成差异，因此当前只可结论为“没有观察到延迟惩罚”，不能宣称增长边使检索加速。
- 正式库运行前后文件大小、修改时间、Association 数量/最大 ID、累计使用次数和最近使用时间全部一致。

这已经把结论从“单条边偶然有效”推进到“在一个预冻结、四条有效边、十二题的批次中重复得到正收益”。它仍不等于跨作品、跨关系类型的统计稳定：样本集中在《伊甸园条约篇》，关系类型以 `contrast` 为主，而且问题是围绕候选设计的。下一阶段应扩大到时间、因果、人物关系、召回触发和多 generation 链，同时加入与边无关的负对照问题，测量误触发率。

候选积累与批量审计仍值得保留，但它是吞吐与稳定性机制，不是通过率优化：

1. 本地先检查候选是否只是已有 Episode 的复述或已有关系的同义表达。
2. 按推论文本、关系类型和前提 Episode 持久去重。
3. 多轮对话积累后批量调用主审；只有主审接受项进入对抗终审。
4. 回答候选默认限定在前台可见的两个 Episode 端点；模型不得自行换端点或扩张邻居。
5. 审计正确拒绝坏样本不应让实验失败；关系类型多样性只作为覆盖信息，不作为强制接受配额。
6. 跨形态候选仍需 identity/variant 证据或保持为明确限定的低置信联想。

### 6.3 实体形态消歧

当前 Concept 允许把“白子”保留为宽泛联想入口，这符合最初设计。但 `favor/10100` 中另一形态白子与普通白子会共享强语义线索，宽松增长由此建立主题对比边。它可能有文学价值，却不能自动当作同一时间线、同一人物状态下的普通关系。

不需要引入庞大的专家系统；可在 Association 和检索元数据中增加少量机器可读限定：

- `entity_variant` 或现有 relation text 中的形态限定；
- `timeline_scope` 一致性检查；
- 无 identity/variant 桥时，跨形态候选只能作为低置信联想，不参与事实型回答。

### 6.4 创造内容的合理性仍有波动

系统已经不再直接把历史 Episode 当成当前任务，但自由创造仍偶尔出现“日奈参与阿拜多斯日常任务”“神秘遗迹”“沙漠观光路线”等可行但不够稳妥的内容。这些内容被正确隔离在私人域，不构成剧情污染；角色扮演质量评测为 4.7/5，但世界观贴合度还有提高空间。

下一步可在不增加模型调用的前提下，为创造性生成提供：

- 当前地点的高相关人物白名单（来自 Concept/Association 得分，而非硬编码角色表）；
- “日常、小规模、可执行、不新增重大组织设定”的创造约束；
- 私人域中已建立的当前任务状态，保证后续消息与任务连续。

### 6.5 专用 BGE reranker 实验

本节区分三个容易混淆的概念：

- **双编码器检索（bi-encoder retrieval）**：问题和 Episode 分别生成 embedding，再用向量相似度快速召回候选；它便宜，但只负责粗筛。
- **交叉编码器重排（cross-encoder reranking）**：把“问题 + 每条候选文本”交给专门相关性模型联合打分；`Pro/BAAI/bge-reranker-v2-m3` 属于这一类。
- **LLM 证据重排**：原系统不是普通相关性排序，而是让通用 LLM 阅读整批候选、判断多个事实槽是否被覆盖，并在必要时做第二次覆盖审计。它能力更广，但调用慢、提示词长。
- **证据下限（evidence floor）**：上游每个原子问题已经命中的锚点，在重排后仍为其保留有限位置。它不创造新事实，只防止一个高分主题挤掉另一个必答事实槽。

SiliconFlow 的正式接口是 `POST /v1/rerank`，输入 `model/query/documents/top_n`，输出候选原下标和 `relevance_score`。实现已加入客户端、查询引擎和 chatbot 配置。现在 `.env` 中只保留一个可选入口：`MEMORY_RERANKER_MODEL` 留空时完全跳过重排，但基础 embedding、sparse 和 Association 检索仍正常执行；填写模型名时表示专用 cross-encoder 可用。不再要求用户同步维护 enabled/backend 两个开关。接口字段参考 [SiliconFlow Rerank API](https://docs.siliconflow.cn/en/api-reference/rerank/create-rerank)。

运行时不会因为配置了模型就全局强制使用 BGE。最终调用策略如下：

| 检索强度 | 模型名为空 | 模型名非空 | trace 标记 |
|---|---|---|---|
| `light` | 不重排 | BGE cross-encoder | `cross_encoder_light` |
| `standard` | 不重排 | BGE cross-encoder | `cross_encoder_standard` |
| `deep` | 不重排 | 原 LLM 多事实槽证据审查 | `llm_deep_default` |
| 后台增长检索 | 不重排 | 原 LLM 证据审查 | `llm_standard` |

普通明确剧情问答现在进入 `standard`，间接人物印象和普通角色扮演进入 `light`；两者在模型已配置时都使用 BGE。`deep` 由问题长度和“为什么、真正原因、逻辑关联、关系、导致、背后、第一次、综合、分析、对比、悖论、因果、推导、证据”等标记触发，并完整恢复为 `LLM + adaptive + always follow-up + 40 个原子问题 + 100 条预压缩候选`。复杂个人记忆问题、以及同时带有创作词和综合分析要求的请求也不再被强制降为 light。

策略只在一次查询持有的 service lock 内临时切换，查询结束或发生普通异常后恢复。协程被取消时会等待仍在运行的 `to_thread` 查询结束，再恢复配置和释放锁，避免旧线程与下一次请求读取同一份可变配置。结果中的 `rerank_policy` 表示计划路径；`rerank_execution` 另外记录实际状态、backend、model、review level、cache hit 和错误。BGE 失败时 standard/light 会明确标为 `degraded` 并退回未重排候选，不会悄悄花费一次 LLM；deep 则从一开始就不会进入 BGE。

实验使用三道冻结的《伊甸园条约篇》多跳题，每题重复三次，共 9 次、27 个事实槽。除了端到端运行，还把历史 LLM 运行时的同一批 64 条候选冻结下来，直接比较排序，避免上游查询规划随机性污染结论。需要特别限定：当时端到端基准直接调用 knowledge service，等价于强制 `standard`，所以它证明的是 BGE 组件收益，不代表当前自动路由会让这些多跳题走 BGE；现在这些题在真实聊天入口会判为 `deep` 并保留 LLM。

| 方案 | 通过 | 事实槽召回 | 平均重排 | 平均全流程 | 说明 |
|---|---:|---:|---:|---:|---|
| 原 LLM 重排 | 9/9 | 27/27，100% | 24.743s | 43.258s | 历史冻结基线 |
| BGE，64 候选 + 证据下限 | 9/9 | 27/27，100% | 1.343s | 26.949s | 与历史基线相同候选规模 |
| BGE，前台实际 30 候选 + 证据下限 | 9/9 | 27/27，100% | 1.083s | 23.428s | 当前最终证据上限为 30 |
| 不重排，独立端到端对照 | 8/9 | 26/27，96.30% | 约 0s | 24.072s | 漏掉一次“阿里乌斯直接执行”事实槽 |

端到端运行显示：BGE 30 候选方案相对历史 LLM 基线平均减少 19.830 秒，约 45.8%；单看重排阶段减少约 95.6%。但是两批端到端请求在不同时间运行，`intent_parse` 的网络与模型波动很大，因此 45.8% 只能当实际观测值，不能当严格配对的稳定加速比。最终复跑的同候选池 API 计时为 BGE 平均 1.392 秒、LLM 平均 24.743 秒，约 17.8 倍。

质量边界比“9/9 通过”更重要。同一批 64 条候选上的结果是：

| 截断位置 | 原候选顺序 | 纯 BGE | BGE + 证据下限 |
|---|---:|---:|---:|
| Top-10 | 77.78% | 77.78% | 66.67% |
| Top-20 | 81.48% | 88.89% | 92.59% |
| Top-30 | 100% | 92.59% | 100% |

这说明专用 reranker 很擅长单条文本相关性，却不天然理解“答案必须同时覆盖爆炸场景、直接执行者和幕后协助者”这种集合覆盖任务。证据下限在 Top-30 能修复损失，但在 Top-20 仍只有 92.59%，没有达到此前要求的 `Recall@20 > 95%`。Top-10 时下限反而会因为名额太少而挤掉另一部分相关证据，这不是实现 bug，而是多事实槽与小预算之间的容量冲突。

同一冻结候选池直接保留原顺序的前 30 条本来也是 100%。因此目前没有证据表明 BGE 能提高基础召回质量；它的明确收益是：在最终保留 30 条且证据下限有效时，以约 1 秒替代约 25 秒的 LLM 重排，同时保持这组题的最终覆盖。独立的“完全不重排”端到端对照虽然更省一次 API，却出现 1/9 失败；由于其上游计划并非与 BGE 逐次配对，这只能作为风险信号，不能把 3.70 个百分点全部归因于 BGE。

多语言探针使用同一条中文 Episode，分别用中文、英文、日文、韩文查询。中文、英文、日文均排第 1；韩文目标排第 2，另一条相近剧情排第 1，即 Top-1 为 3/4。当前样本太少，不能证明稳定的跨语言能力，尤其不能把韩文问题直接视为与中文同等可靠。

当前建议不是全局替换，而是自适应分工：

1. 配置了模型时，轻量和普通剧情问答都使用 BGE；小数据库确定性快速路径仍跳过远程重排。
2. 中文普通剧情问答在最终证据预算为 30、上游证据下限完整时使用 BGE。配置的预压缩目标是 24，但会被最终证据数量下限抬到实际 30。
3. Top-20、小语种、事实槽很多、否定/因果/身份消歧或上游锚点不完整时，保留 LLM 证据审查。
4. BGE 请求失败时返回正常检索候选并记录错误，不悄悄调用昂贵 LLM；是否升级到 LLM 应由会话强度路由显式决定。

在强制 `standard` 的实验路径中，BGE 消除了原流程最大的 `evidence_rerank` 瓶颈，新的主瓶颈变成 `intent_parse`：30 候选实验平均 11.780 秒，占全流程 50.3%。`deep` 仍主动保留原 LLM 延迟。若继续优化重度剧情问答，下一阶段应在不牺牲多事实槽覆盖的前提下冻结/缓存查询计划、减少意图解析调用。

## 7. 当前阶段结论

本阶段可以确认：

- 用户、公共、剧情三个记忆域的架构分离有效；
- 创造性角色扮演内容可以保存为私人记忆且不污染原作节点；
- 剧情库没有被永久设为只读，回答内的新推论仍有受证据约束的增长通道；
- 同一次模型调用的隐藏候选方案比二次整理调用更快、更安全；
- 简单 RP 快速路径基本可用，但五秒目标尚未稳定覆盖直接剧情问答；
- 专用 BGE reranker 已证明可以显著替代前台 LLM 重排的时间成本，但没有证明能提高基础召回；Top-20 质量仍不足，因此暂时只作为可选前台后端，不全局启用；
- 自动剧情增长目前“安全性已验证、冻结多边批次的重复正收益已验证、跨领域统计稳定性未验证”；下一阶段重点应是扩大关系类型、加入负对照问题和测试多 generation 链，而不是放宽持久化门。
